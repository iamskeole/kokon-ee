## window footguns (w030, 2026-11-17 — read before building a box window)

Learned the hard way across seven window attempts (runs 1–6: the
window's own; run 7: the window's gate typo plus the owner's protocol
correction — the daemon and the box behaved as designed each time):

1. **A window never writes the registry (owner-corrected 2026-11-17 —
   the neutralization design is a pre-matrix legacy; the 0.12.1-era
   task-028 windows never touched the gateway file).** The matrix
   router owns the eviction (a qwen request evicts vllm; FIFO deferral
   protects a running job; chat is the priority tenant), and the
   daemon's ON-DEMAND start is the revival — the owner's next chat
   after a window brings vllm back as the daemon's own child, so the
   agent session (the window's blocker) resumes with inference working.
   The window therefore stops the vllm process (group signal — process
   level, not config level), runs its jobs, and revives vllm before the
   marker (1-token gateway request → the daemon's own cmd; boot script
   as fallback). The agent is suspended while the window blocks, so
   nothing needs inference mid-window by design. (The older mechanics —
   a registry edit must stay a valid config or `reload()` keeps the old
   in-memory one, and a dangling matrix reference fails the whole load
   (`matrix: var key "v" references unknown model …`) — remain true for
   any future manual edit, but the window doesn't make one.)
2. **`/health` lies through an in-process reload** (the listener never
   stops). `/v1/models` flips to the new registry at the mux swap, but
   `/upstream/<model>/*` can keep 500-ing until the old server's teardown
   finishes (a few to a few tens of seconds). Gate on the exact endpoint
   the client will call (e.g. `/sdcpp/v1/capabilities`) returning 200 —
   the probe doubles as the engine's first load, which the job wants
   anyway.
3. **The daemon's in-memory store survives reloads: a reload re-runs the
   cmd of any model the store marks loaded** (the "revive dead registry
   models" behaviour — and the canonical revival). A vllm booted *outside*
   the daemon (a setsid revival from a prior force-end) is not a daemon
   child, so the daemon's group signal can never stop it — the next
   window's neutralization cannot free the card and yields. Since w030
   run 5 the window stops every live vllm itself first, by its own
   process-group signal (v269's own stop semantics — it works on the
   daemon's child and on orphans alike). The revival after the window
   is the daemon's ON-DEMAND start (a 1-token gateway request — the
   daemon runs the configured cmd as its own child, the cleanest
   ownership); the canonical boot script is the fallback (it attaches
   if anything appeared meanwhile); verify with the 1-token
   `/v1/completions` probe, never `/health`. (If the daemon re-runs a
   cmd while an external instance holds the port, the duplicate dies on
   `Address already in use` — a harmless flap that can cut one in-flight
   stream, which recovers.)
4. **The service rewrites `data/service.json` at startup** (port/token/
   pid/version) — a read racing the boot sees the file missing; retry the
   read, never FATAL on it.
5. **`500 "upstream command exited prematurely" is a preflight failure**
   (missing file, bad exec, dangling `LD_LIBRARY_PATH`) — the only
   symptom; read the journal's boot lines before touching anything else
   (task-028's D-RN3, still true).
6. **Never probe `/upstream/<loaded-model>` on a live box outside a
   window** — the request goes through the load/revive machinery and can
   flap that model's process (observed: a capabilities probe triggered a
   vllm cmd re-run that died on the port bind).
7. **The 0.12.1 service image is a no-op migration for the box config**
   (schema 15 passes the chain untouched — proven in vivo: byte-identical
   across the live container swap) and the image swap itself is CPU-side;
   the GPU phases are only the proof jobs and the vllm cycle.
